# Mobile Friends: two-user Android walkthrough

Use an Android development client and two onboarded test accounts, Alice (`alice_1`) and Bob (`bob_2`), with a backend approved for manual testing. Use two devices/sessions, or sign out when switching accounts on one device. These device checks have not been performed in this workspace. Automated tests mock Auth/API and do not modify live data or send notifications. The [friendship contract](friendships.md) and [profile-search contract](../README.md#profile-onboarding-and-api) remain unchanged; this feature needs no backend changes or migrations.

1. As Alice, open **Home → Friends**. Verify loading and separate empty states for accepted friends, incoming requests and outgoing requests. Sign out and try the `/friends` route or Android Back: Friends must remain protected. A signed-in user without a profile must complete onboarding before entering.
2. Search for ` BOB_2 ` and expect only Bob's current display name and `@bob_2`. Input is trimmed and lowercased, then validated as 3–30 ASCII letters, digits or underscores. Invalid input must show validation feedback. Search for an absent username, Alice's own username and a prefix of Bob's username that is not another exact username: show no matching profile, with no suggestions or directory. No email, timezone or Auth metadata appears.
3. Send Bob a request. Repeated taps during a delayed response must issue one mutation. Alice sees Bob under outgoing requests with no cancellation action. As Bob, refresh or return to Friends and find Alice under incoming requests. **Reject** once; refresh Alice's screen and verify the outgoing request disappears. Alice can then search and send again. Bob **Accepts** the new request; both accounts show each other under accepted friends after refresh, with no pending request left.
4. Change a test account's display name/username through the existing profile API, then refresh the other account's Friends screen. Lists must show the current identity; searching the new exact username must work. Navigate away and return to confirm focus refresh, and exercise manual refresh on empty and populated lists.
5. Remove the accepted friend. Read the confirmation: removal deletes habit sharing in both directions, and becoming friends again does not restore those grants. Cancel once and confirm the friendship remains. Confirm removal and verify both accounts' refreshed accepted lists are empty. Send and accept a new request to verify friendship can resume; any pre-existing sharing grants must stay removed. Sharing management itself has no controls on Friends.
6. With controlled concurrent sessions, send the same request twice, send in the reverse direction while pending, and send after acceptance. Expect readable conflict feedback and refreshed lists reflecting the existing relationship. Accept/reject a request already decided elsewhere, or remove a friendship already removed elsewhere: reconcile the current lists without treating the stale row as actionable. A removed recipient profile must clear the unusable search result; a missing caller profile must clear stale identities and explain how to return Home, sign out and sign in again to complete onboarding.
7. Using mocked delays/failures, test initial load failure, refresh failure, search failure and an expired session. Retry reads after restoring connectivity; never show an empty-success message for a failed load. A lost mutation response, timeout or server failure may mean the write succeeded: refresh current server state before offering another mutation, and keep mutations blocked if reconciliation fails. A failed refresh after a confirmed write must retry the read, never repeat that write. Verify a same-account token refresh preserves pending-action guards and later requests use the refreshed token.
8. Delay Bob's search response, edit the query and search again, then release the older success and failure responses: neither may replace the current query's result or error. Repeat while clearing or invalidating the input. During pending searches, list reads, confirmations and mutations, sign out or switch to the other account: prior identity, lists, query, errors and confirmations must clear; late responses must not repopulate them or act for the new account.
9. On Android, check Back navigation, keyboard/scroll behavior, refresh gestures on short and empty lists, long display names, removal confirmation and screen-reader labels/reading order. Recheck Home navigation and normal sign-in/sign-out.

Run `npm test` and `npm run typecheck` from `mobile/`. Mocked API/store/screen coverage verifies endpoint bodies and public identity, normalization, the full request/decision/removal workflow, repeated taps, conflicts, failed and uncertain writes, stale searches/list refreshes, account isolation and in-flight guards across route remounts. Native Android rendering, gestures, accessibility, emulator/physical-device execution, EAS builds and live Auth/API behavior remain untested here. This milestone adds no partial search, user directory, request cancellation, mobile habit-sharing/reminder/excuse controls or social notifications.
