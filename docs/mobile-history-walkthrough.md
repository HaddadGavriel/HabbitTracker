# Mobile owner history and current streak walkthrough

Use an Android development client and an onboarded test account with a backend approved for manual testing. These device checks have not been performed in this workspace. Automated tests use mocked APIs and sessions, never live data. The [backend history contract](history.md) defines ordering, snapshots, compact excuses and streak semantics.

1. Open **Home → My habits → Active**, then a habit's **View history** link. Repeat from **Archived** without restoring the habit. Both views must open the protected history screen; active editing and archived restore controls must still work. Sign out and try a `/habit-history?id=...` deep link: history must remain protected. A missing/foreign habit must show a useful error and no other owner's records.
2. Expect independent loading indicators for history and current streak. Compare the streak number, provisional flag and calculation timestamp with `GET /habits/{id}/streak`. A provisional streak must be clearly labeled, including when the count is zero. The count comes from the entire server-calculated sequence, not the visible history page. A stable zero is valid.
3. Compare rows with `GET /habits/{id}/history`: newest stored `local_date` first, with UUID descending for ties. Verify historical names/descriptions, type, target/unit, schedule, progress and state come from each occurrence's snapshot. Check stored timezone and deadline; changing the device timezone must not shift the displayed occurrence date. Current habit edits must not rewrite historical labels or target thresholds.
4. With controlled records, inspect all five occurrence states and a target with partial, zero and over-target progress. Check compact excuses with pending, automatic approval, friend approval and friend rejection: explanation, status and available decision details should remain readable. No progress, completion, excuse or decision controls belong on this screen.
5. Use a habit with more than 30 occurrences. Press **Load more** and verify one request using the exact opaque `next_cursor`, older rows appended without duplicates, and no further Load more once the cursor is null. Repeated taps during a delayed page request must send only one request. A failed page preserves existing rows and offers a retry for that page.
6. Pull to refresh after loading multiple pages. Refresh restarts at the first page and resets pagination. Delay an older Load more response until after refresh succeeds; it must not append stale rows or restore its cursor. Repeat with the older request failing, with a refresh failure followed by retry, and with overlapping/repeated refresh gestures.
7. Fail only the streak request. Successfully loaded history must stay visible and usable, with a separate streak retry. Fail only history: a successfully loaded streak must stay visible, with a history retry and no empty-success message. Test both failing, an empty successful history, and a failed refresh with previously loaded data; loading, stale-data and retry messages must be clear. Retrying one failed section must not discard the successful section.
8. While requests are delayed, navigate to another habit, leave/reopen history, sign out or switch accounts. Previous rows, cursors, streaks, excuse text and errors must not leak into the new context. Late pages and failures must be ignored. Renew the same account's token and verify subsequent requests use the new token. Reopen history after changing progress on Today and verify the refreshed server streak/history.
9. On Android, check Back navigation, long-list scrolling, pull gestures on short/empty lists, loading/error layouts, long excuse text, and screen-reader reading order/labels. Recheck the existing creation/edit/archive/restore and binary Complete/Undo flows.

Run `npm test` and `npm run typecheck` from `mobile/`. Mocked API, state and screen-control tests cover cursor encoding, duplicate prevention, pagination/refresh races, partial failures, provisional streaks, archived access and account isolation. Native Android rendering/gestures/accessibility, emulator/physical-device execution, an EAS APK build and live Auth/API verification were not performed. No backend code or migrations change. This milestone adds no date filters, locally calculated/longest streaks, charts, advanced analytics, friend/sharing flows, excuse actions or notifications.
