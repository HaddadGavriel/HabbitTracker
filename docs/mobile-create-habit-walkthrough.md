# Mobile habit creation walkthrough

Run this checkout in an Android development client configured with the public values in `mobile/.env.example`. Use an onboarded test account and a backend approved for test habit creation. No backend release or migration is needed. Automated tests use mocked APIs/Auth and do not create live data. Device steps below have not been run in this workspace, which has no Android device or configured test credentials.

1. Open **Home → My habits → Create habit**. Submit the empty form: expect a readable name error and no request. Enter a name, optional description, **Binary (yes/no)**, **Every day**, and reminder times `08:00, 21:30`. The form explains these are saved settings, in the profile timezone; notification scheduling is not implemented.
2. Tap **Create habit** twice quickly. Expect a single POST, disabled controls and loading feedback. On success, expect **My habits** to reload and show the new habit with its daily/binary details. If the list read fails, use its **Retry**; this must not repeat creation.
3. Create a target habit with an integer such as `20`, optional unit `pages`, **Selected weekdays**, and Monday/Sunday. Verify the populated list shows the amount/unit and correct weekday names. Also try a target without a unit. Binary requests must omit target/unit even after switching from Target; daily requests must have empty weekdays even after selecting days.
4. Validate failures: blank/overlong name, overlong description/unit, zero/negative/fractional target, selected schedule without days, blank reminder times, duplicate `08:00, 08:00`, malformed `8:00`, and out-of-range `24:00`. Correct values and resubmit; entered values should remain. The app accepts up to 100 Unicode characters for name, 1,000 for description, 30 for unit, and a target up to JavaScript's exact integer limit (9,007,199,254,740,991).
5. With a mock/proxy returning a definite 401/422 failure, verify a readable error and preserved draft. With a delayed/lost response or HTTP 5xx, verify the uncertainty warning and **Check My habits** / **Submit again** choices. Waiting or changing screens must never retry the POST. **Check My habits** opens a refreshed list; use Back to return to the same draft. Only submit again after checking whether the habit already exists. The backend has no creation idempotency key, so an explicit second submission can create a duplicate.
6. While a mocked creation is pending, trigger sign-out or account switching. The old draft, error and result must disappear; late responses must not navigate or affect the new account. A normal same-account token refresh must retain the draft and in-flight submission guard. On the next submission the API must use the current access token.
7. Verify `/create-habit` is inaccessible when signed out or still onboarding. Check Android Back, keyboard scrolling, multi-line description entry, and accessibility labels/selected states. Existing authentication, onboarding and diagnostics should behave as before; do not trigger notifications for this walkthrough.

Run `npm test` and `npm run typecheck` in `mobile/`. Mocked coverage checks payloads, validation, creation/list refresh, failures/uncertain results, duplicate prevention and stale-account protection. Native navigation, keyboard behavior and real test-account creation remain manual checks.
