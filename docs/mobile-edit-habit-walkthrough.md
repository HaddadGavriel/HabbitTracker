# Mobile habit editing walkthrough

Use an Android development client configured with `mobile/.env.example`, an onboarded test account with existing active binary/target habits, and a backend approved for test edits. Automated tests mock Auth/API and never modify live data. These device steps have not been run in this workspace; no Android device or test credentials are configured.

1. Open **Home → My habits** and tap an active habit. Expect a loading indicator before its current saved configuration appears. Type is read-only. Change a name and save; expect one PATCH, then a refreshed **My habits** list showing the new name. Reopen to verify the saved values.
2. Edit description, target/unit where applicable, weekdays and reminder times. Clear description/unit and save: the request should contain `null` for those cleared fields, omit unchanged fields and never include type. Binary habits have no target/unit controls. Saving without changes should make no request. An unchanged target beyond JavaScript's exact integer range must remain omitted when editing another field.
3. Select Monday/Sunday, switch to **Every day**, then back to **Selected weekdays** before saving: the selections should remain. Saving daily sends schedule plus empty weekdays; saving selected sends schedule plus selected weekdays when the schedule changes. Try an empty selected schedule, nonpositive/fractional target, empty/duplicate/malformed reminder times and an empty name: expect readable errors with values preserved. Reminder times are saved settings; notifications are not scheduled.
4. With a mocked/proxied initial GET failure, expect an error and **Retry loading**. With a 404 or archived result, expect an unavailable message and no editable form. A PATCH returning `habit_not_found`/`habit_archived` must also block further edits.
5. Tap **Save changes** twice quickly during a delayed request: expect one PATCH and disabled fields. A definite 401/422 failure preserves edits and permits an explicit retry. After a lost/delayed response or HTTP 5xx, expect a warning that the save may have succeeded and **Reload saved configuration**. Read the warning that reloading replaces unsaved edits, then reload: successful GET replaces the draft with server values; a failed GET preserves it. No timeout, reload, token refresh or navigation should automatically retry PATCH.
6. During mocked pending reads/saves, navigate back or switch/sign out of the account. Late results must not repopulate the editor or navigate for the new account. Reopening the editor reads fresh values. Normal same-account token refresh retains the draft and duplicate-save guard.
7. Check keyboard scrolling, multiline description, Android Back and accessibility labels. Signed-out/onboarding users cannot open `/edit-habit`. Smoke-check creation (including retained weekday selections), authentication, onboarding and diagnostics.

Run `npm test` and `npm run typecheck` from `mobile/`. Mocked tests cover the GET/PATCH contract, minimal payloads and null clearing, schedule transitions, shared form handlers, loading/unavailable states, save/list refresh, failures, ambiguity, duplicate prevention and stale responses. Native navigation and device behavior remain manual checks.
