# Mobile Today and target progress walkthrough

Use an Android development client with an onboarded test account and a backend approved for manual testing. Device checks have not been run in this workspace. Automated tests mock Auth, API, navigation and app lifecycle; they never use live data. Owner history and current streak checks are in [the history walkthrough](mobile-history-walkthrough.md).

1. Sign in and open **Home → Today**. Expect a loading indicator, then the server's local date and timezone. Compare the cards with that account's `GET /today` response: names/types come from each occurrence's snapshot, target cards show progress/target and an optional unit, and all returned rows remain in server order. An archived habit's retained occurrence must still appear when returned. A successful empty response shows its date/timezone and **No habits to show for this date.**
2. Before a binary occurrence's deadline, press **Complete** on an **In progress** card. Expect loading on that card, duplicate presses to send no additional request, then the confirmed **Completed** state and **Undo**. Press **Undo** and expect the confirmed **In progress** state and **Complete**. Each request sends an explicit `completed` boolean to `PUT /occurrences/{id}/completion`; each success refreshes Today.
3. Before a target occurrence's deadline, enter an absolute progress value and save it. For a snapshot target of 10 pages, save 3, then 10, then 4: expect **In progress**, **Completed**, then **In progress** again. Zero and over-target values are allowed. Verify the current server progress appears separately from the value being entered. Change the habit's configured target/unit through the existing edit flow and return to Today: this occurrence must retain its original snapshot threshold/unit. Repeat with a target without a unit. No increment/decrement shortcuts are provided.
4. Try blank input, a negative value, a fraction, exponent notation, and `9007199254740992` (above JavaScript's safe integer range). Expect validation with no write and no silent rounding. With a delayed mocked save, press save twice: only one `PUT /occurrences/{id}/progress` request with an absolute integer may be sent. The busy indicator and errors belong to that card; another eligible card remains usable.
5. Binary and target **Missed**, **Excuse pending** and **Excused** cards offer no mutation. Neither completion nor progress is offered at or after `closes_at`, including completed cards. The device timezone must not reinterpret the stored date, deadline or status. The backend remains the final authority on eligibility.
6. Simulate `409 occurrence_closed` and `409 occurrence_locked` after an eligible card was loaded. Expect a per-card explanation and a Today refresh, with no false success. Simulate a definite validation/authentication rejection: retain the typed progress and show a useful error. For timeout, connection loss, 5xx or an invalid success response, expect a refresh option and no further write until a successful refresh. A failed refresh must preserve the entered value and the guard. Restore connectivity and refresh to learn the current server state; no mutation retries automatically.
7. Simulate an initial offline/401/5xx/timeout loading failure. Expect a readable error and **Retry loading**, with no invented date or empty-success message. Pull down on a loaded list, including an empty list. After a failed refresh across midnight, the old date, timezone and cards remain together with **Showing the last loaded date and habits.** A successful retry replaces the date and rows together; an empty result removes the old rows.
8. With controlled response delays, start a refresh, save target progress, then release the older refresh. It must not overwrite the confirmed result. Repeat with a reduction and with binary Complete/Undo. If a refresh switches to a new server date while a mutation is pending, release the old mutation afterward: it must not insert the old occurrence, draft or error into the new day. A failed post-save refresh must leave the confirmed server result visible.
9. Return Home and reopen Today: expect a fresh read. Background and foreground the app while Today is visible: expect another read, including across midnight. Repeat while Home is visible: Today must not fetch in the background. Check Android Back, scrolling, pull-to-refresh, numeric keyboard, keyboard dismissal and screen-reader labels on device.
10. With delayed mocked reads and mutations, leave/reopen Today, sign out, switch accounts and renew the same account's token. Leaving or changing accounts must clear the previous date, rows, drafts and errors. Late results must not repopulate them or overwrite a newer result. If the same occurrence reappears with an earlier request still pending, keep its action disabled; after that request settles, refresh before another change. Token renewal keeps loaded data while reading with the new credentials.
11. Recheck existing habit creation, editing, archive and restore using their walkthroughs. Archiving must preserve today's already-created obligation, and restoration must not duplicate or reset it.

From `mobile/`, run `npm test` and `npm run typecheck`. API, state and screen-control tests use mocked dependencies and exercise actual handlers, including target reduction, strict integer validation, locked/deadline rejection, ambiguous outcomes, refresh races, navigation, midnight and account isolation. They do not verify native rendering or gestures. Android device/emulator execution, an EAS APK build, live Auth/API behavior and the manual steps above were not performed. No deployment, shared database migration or live-data automated test is part of this milestone. The [mobile excuse walkthrough](mobile-excuses-walkthrough.md) covers eligible Today submission, existing excuse details and final friend decisions. Excuse notifications remain deferred.
