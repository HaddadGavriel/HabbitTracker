# Mobile Today and binary completion walkthrough

Use an Android development client with an onboarded test account and a backend approved for manual testing. Device checks have not been run in this workspace. Automated tests mock Auth, API, navigation and app lifecycle; they never use live data.

1. Sign in and open **Home → Today**. Expect a loading indicator, then the server's local date and timezone. Compare the cards with that account's `GET /today` response: names/types come from each occurrence's snapshot, target cards show progress/target and an optional unit, and all returned rows remain in server order. An archived habit's retained occurrence must still appear when returned. A successful empty response shows its date/timezone and **No habits to show for this date.**
2. Before a binary occurrence's deadline, press **Complete** on an **In progress** card. Expect loading on that card, duplicate presses to send no additional request, then the confirmed **Completed** state and **Undo**. Press **Undo** and expect the confirmed **In progress** state and **Complete**. Each request sends an explicit `completed` boolean to `PUT /occurrences/{id}/completion`; each success refreshes Today. The displayed date/timezone always come from the server response.
3. Using controlled responses, verify target habits remain read-only, including completed targets, progress above target and targets without a unit. Binary **Missed**, **Excuse pending** and **Excused** cards have no completion action. Neither Complete nor Undo is offered at or after `closes_at`. The device timezone must not reinterpret the server's date, schedule or status; the backend remains the final authority on deadlines and eligibility.
4. Simulate a completion response of `409 occurrence_closed` or `409 occurrence_locked` after an eligible card was loaded. Expect a clear per-card explanation and a Today refresh, with no false success. Simulate other rejected requests and verify the error stays with the affected occurrence. For a timeout, connection loss or otherwise uncertain mutation outcome, expect a refresh option before another action. Restore connectivity and refresh to learn the server's current state; no mutation retries automatically.
5. Simulate an initial offline/401/5xx/timeout loading failure. Expect a readable error and **Retry loading**, with no invented date or empty-success message. Restore the connection and retry. Pull down on a loaded list (including an empty list): expect the refresh indicator and an updated server response. After a failed refresh across midnight, the old date, timezone and cards remain together with **Showing the last loaded date and habits.** A successful retry replaces the date and rows together; an empty result removes the old rows.
6. With controlled response delays, start a refresh, complete a binary occurrence, then release the older refresh. It must not overwrite the confirmed completion. Repeat with Undo. If a refresh switches to a new server date while a mutation is pending, release the old mutation afterward: it must not insert the old occurrence into the new day or alter that day's cards/errors.
7. Return Home and reopen Today: expect a fresh read. Background and foreground the app while Today is visible: expect another read, including across midnight. Repeat while Home is visible: Today must not fetch in the background. Check Android Back, scrolling/pull-to-refresh and screen-reader labels on device.
8. With delayed mocked reads and mutations, leave/reopen Today, sign out, switch accounts and renew the same account's token. Leaving or changing accounts must clear the previous date, rows and errors. Late successes and failures must not repopulate them or overwrite a newer result. If the same occurrence reappears with an earlier request still pending, keep its action disabled; after that request settles, refresh before another change. Token renewal keeps already-loaded data while reading with the new credentials.

From `mobile/`, run `npm test` and `npm run typecheck`. Focused API, Today store and screen tests cover explicit completion/undo requests, real screen control presses with mocked dependencies, eligibility, duplicate prevention, failures, refresh races and stale results, alongside loading/empty/error/retry, date retention, focus/foreground refresh and account isolation. These automated checks do not replace the unperformed device walkthrough. The existing backend owns occurrence generation, reconciliation, deadlines and states. Target progress, excuses, streaks, history and notifications are outside this mobile milestone; no backend or migration changes are needed.
