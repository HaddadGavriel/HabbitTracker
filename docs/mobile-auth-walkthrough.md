# Android authentication and onboarding walkthrough

Use an Android development/preview build configured with the public environment values in `mobile/.env.example`. Use the existing backend; this change needs no new migration. Run `npm ci`, `npm test`, and `npm run typecheck` in `mobile/`. CI uses Node 22 and the committed package-lock.json. Tests mock Auth and API calls; they never send notifications.

1. Launch signed out. Open **Create an account**, enter email/password, and tap **Sign up** once. With email confirmation enabled, verify the confirmation message appears without onboarding. Follow the email link in your email/browser, return to the app, and sign in. This app does not consume email-link sessions. With confirmation disabled, sign-up may proceed directly to onboarding.
2. Enter username, display name, and the suggested device IANA timezone; correct it if needed. Try an invalid username and a taken username, then create a valid profile. Verify home displays normalized identity and timezone. An existing Auth account without a profile must also see onboarding.
3. Force-close and restart. Verify a loading screen precedes home and the persisted session restores. Background/foreground the app and verify the session remains usable after token refresh.
4. Temporarily make the API unreachable during profile loading. Verify retry UI appears, not onboarding. Restore connectivity and tap **Retry**. Only `profile_not_found` opens onboarding.
5. If profile creation times out or loses its response, tap **Check whether my profile exists**. A created profile opens home; an absent profile returns to onboarding, and a network failure offers retry. No creation is automatically retried. **Submit again** is an explicit user decision. An existing-profile conflict reloads the profile.
6. From home open **Infrastructure diagnostics**, then go back. Sign out and press Android Back repeatedly; home/diagnostics must remain inaccessible. Restart and verify signed-out state.
7. Sign in as a second account. Verify none of the first account's identity, onboarding fields, registration status, result, or notification receipt remains. Repeat switching during a slow profile request. Diagnostic registration starts unregistered for each account/mount.
8. On a physical Android device, open diagnostics, tap **Register notifications**, and grant permission. Only when intentionally testing delivery, tap **Run Infrastructure Test** and compare its request ID and timing stages to the real remote notification. Repeat foreground/background delivery per [Android push setup](android-push-setup.md). These actions use the existing registration and push endpoints and can send a real notification.

Automated coverage checks the session controller, route guard policy, profile normalization/conflicts, stale responses, and the existing API contracts/errors/deadlines. Native screen rendering, keyboard behavior, accessibility, Android Back/history, email delivery/confirmation, persistent AsyncStorage, AppState token refresh, and physical push receipt require the above manual device walkthrough; they are not claimed as verified by Node tests.
